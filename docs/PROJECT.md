# Production Forecast Copilot – Project Documentation

> Living document. Updated at the end of each stage. Stage status lives in [`PROGRESS.md`](PROGRESS.md).

## 1. Purpose
A small portfolio MVP showing an end-to-end Data & AI workflow for **production planning** in a
manufacturing / ERP context. It forecasts how many units a production line will produce in each of the
next 24 hours, and an LLM explains that forecast in plain language for a production planner
(digital-twin style view of the line).

This is a production project, not an energy project: the signal is **units produced**, not kWh or load.

## 2. Domain & target
- **Signal:** hourly output of one production line (`units_produced`).
- **Forecast target:** the next 24 hourly `units_produced` values.
- **Planner questions it answers:** When is output highest/lowest tomorrow? Where are the dips
  (shift changes, planned maintenance)? How does tomorrow compare with today?

## 3. Data source – simulated production line
No public dataset with real hourly production output was found (companies rarely publish it; searched
Hugging Face, Oct 2026). The data is therefore generated by a small Python **production-line simulator**
("digital twin") and is always labelled as simulated.

Simulator: `forecasting/simulate.py` (run `python simulate.py` in `forecasting/`, seed 42 → reproducible).
- 2 years hourly (Oct 2024 – Sep 2026), one line, nominal 120 units/h.
- Shifts: early 06–14, late 14–22, night 22–06 Mon–Fri; Saturday early only; Sunday and holidays off.
  Efficiency early 100 %, late 97 %, night 90 %; first hour of each shift 85 % (handover).
- Planned maintenance: every 2nd Saturday early shift (0 output).
- Breakdowns: random, ~1.5/week, 1–4 h, 0 output (not forecastable).
- Changeovers: ~2/week, product A/B/C, 40 % output in that hour, extra scrap.
- Noise ±5 %, scrap 2–4 % → `good_units`.

Output: `data/production_hourly.csv` – columns `timestamp, shift, product, status, units_produced,
scrap_units, good_units`. Target = `units_produced`. `status` is for exploration and LLM context only
(not a model feature – unknown in the future).

Exploration: `forecasting/notebooks/01_explore.ipynb`. Baseline MAE on the last 8 weeks:
same hour yesterday **40.6**, same hour last week 16.3 units/hour.

## 4. Architecture
```
data/ (simulated CSV) → forecasting/ (Python: pandas, scikit-learn, FastAPI)
                      → backend/ForecastCopilot.Api (ASP.NET Core, typed HttpClient, Chart.js UI)
                      → LLM (local Ollama by default) writes a short summary for the planner
```
Docker Compose runs both services. Azure deployment is optional.

## 5. Forecasting approach
- Model: RandomForest / GradientBoosting (`forecasting/train.py`); the one with the lower test MAE is saved.
- Features (`forecasting/features.py`): hour of day, day of week, lag 24h, lag 168h. All are known 24 h
  ahead, so one model predicts each of the next 24 hours directly (no recursive forecasting).
- Split: time-based, last 8 weeks = test set (never shuffled).
- Baseline: "same hour yesterday". The model must beat it on MAE (mean absolute error).
- Results (test MAE, units/hour, simulated data):

  | Model | MAE |
  |---|---|
  | Baseline: same hour yesterday | 40.6 |
  | Baseline: same hour last week | 16.3 |
  | RandomForest (saved) | **10.3** |
  | GradientBoosting | 10.5 |

  Remaining error is mostly random breakdowns, which cannot be forecast.
- The LLM never produces numbers; it only describes the structured forecast JSON.

## 6. How to run
```bash
cd forecasting
python -m venv .venv && .venv/bin/pip install -q -r requirements.txt
.venv/bin/python simulate.py   # regenerate data/production_hourly.csv (seed 42)
.venv/bin/python train.py      # train → model/model.joblib (gitignored) + model/metrics.json
.venv/bin/uvicorn app:app --reload --port 8000   # API → http://localhost:8000/docs
```

### Python API (`forecasting/app.py`)
- `GET /health` → `{"status": "ok"}`
- `GET /forecast` → next 24 hours after the last actual hour in the CSV:
```json
{
  "data_source": "simulated production line",
  "model": "random_forest",
  "mae": {"model": 10.3, "baseline_same_hour_yesterday": 40.61},
  "last_actual_timestamp": "2026-09-30T23:00:00",
  "forecast": [
    {"timestamp": "2026-10-01T00:00:00", "units_predicted": 108, "units_same_hour_yesterday": 107}
  ]
}
```
`forecast` has 24 entries. `units_same_hour_yesterday` is the naive baseline (actual output 24 h earlier).

### .NET app (`backend/ForecastCopilot.Api`, ASP.NET Core MVC)
```bash
# Python API must be running on port 8000 (see above)
dotnet run --project backend/ForecastCopilot.Api   # → http://localhost:5088
```
- `GET /` → forecast page: KPI cards, Chart.js line chart (forecast vs. same hour yesterday), hourly table.
- `GET /api/forecast` → same JSON as the Python `/forecast`; `502` ProblemDetails if Python is unreachable.
- Config: `ForecastApi:BaseUrl` in `appsettings.json` (default `http://localhost:8000`);
  override with env var `ForecastApi__BaseUrl` (e.g. in Docker).
- Solution file `ProductionForecastCopilot.slnx` at the repo root (open it in Rider).
- `GET /Home/Summary` → `{ "summary": "..." }` LLM planner summary (fetched by the page after render);
  `503 { "error": ... }` if Python or Ollama is unreachable – the rest of the page still works.

### LLM (local Ollama)
- Ollama runs as a systemd service on `localhost:11434` (starts at boot; loads the model on first request,
  unloads after ~5 min idle). Check with `ollama ps` / `systemctl status ollama`. No API key, data stays local.
- Config section `Llm` in `appsettings.json`: `Provider` (`ollama`), `Ollama:BaseUrl`, `Ollama:Model` (`qwen3.5`);
  override with `Llm__Provider`, `Llm__Ollama__BaseUrl`, `Llm__Ollama__Model` (see `.env.example`).

## 7. Stage notes
### Stage 3 – Data
- Decided: simulated production line (no real public hourly production data); target = units produced.
- Dropped: UCI steel-plant energy dataset (energy consumption does not fit a production-planning project).
- Built: production-line simulator (`forecasting/simulate.py`) → `data/production_hourly.csv` (17,520 rows).
- Built: exploration notebook `forecasting/notebooks/01_explore.ipynb` with plots and naive baseline MAE.

### Stage 4 – Forecasting
- Built: `features.py` (shared with the API in Stage 5) and `train.py` (split, baselines, RF vs. GB, save).
- Result: RandomForest MAE 10.3 vs. 40.6 (same hour yesterday) and 16.3 (same hour last week).
- Decided: model binary (~33 MB) is gitignored and regenerated by `train.py`; `metrics.json` is committed.

### Stage 5 – Python API
- Built: FastAPI `app.py` with `/health` and `/forecast`; Pydantic models define the JSON contract for .NET.
- Approach: append 24 empty future hours to the series and reuse `make_features` (lags point into known history),
  so training and serving share one feature function.
- Model + metrics are loaded once at startup; the CSV is read per request (small, picks up new data).

### Stage 6 – .NET application
- Built: ASP.NET Core MVC app (.NET 10) with typed HttpClient `ForecastApiClient` registered via `AddHttpClient`
  (IHttpClientFactory → pooled connections, no socket exhaustion; 10 s timeout).
- C# records in `Models/ForecastResponse.cs` mirror the Pydantic models; `[JsonPropertyName]` keeps snake_case JSON.
- Errors: the client turns "service down / timeout / bad JSON" into `ForecastApiUnavailableException`;
  `/api/forecast` returns 502 ProblemDetails, the page shows a friendly message, details go to the log.

### Stage 7 – UI
- Built: KPI row (units next 24 h, change vs. previous 24 h, peak hour, MAE vs. baseline), Chart.js line chart,
  hourly table with coloured change column; dark navbar, cards, "Simulated data" badge.
- KPIs are computed in C# (`ForecastPageViewModel`), not in JS – deterministic, reusable as LLM input in Stage 8.
- Chart data: Razor embeds the forecast as `<script type="application/json">` (one Python call per page load);
  `wwwroot/js/forecast-chart.js` reads it with `JSON.parse` (no inline JS).
- Chart.js 4.5.1 vendored in `wwwroot/lib/chart.js/` (works offline / in Docker, like Bootstrap).

### Stage 8 – LLM
- Flow: `ForecastFacts.From(forecast)` (C#) → facts JSON → `ForecastSummaryService` (prompt) → `ILlmClient`
  → `OllamaLlmClient` (`POST /api/chat`, `stream:false`, `think:false`, temperature 0.2, timeout 60 s).
- The LLM never computes numbers: `ForecastFacts` precomputes totals, change %, peak / lowest producing hour,
  no-production periods, top 3 drops vs. yesterday (incl. differences) and MAE; the prompt allows only numbers
  that appear literally in the JSON. KPI cards read the same `ForecastFacts`, so UI and summary always match.
- Hour labels use `InvariantCulture` (English day names regardless of OS locale).
- Async loading: `wwwroot/js/forecast-summary.js` fetches `/Home/Summary` and sets `textContent` (no HTML → no XSS).
- New provider = new `ILlmClient` class + one case in `Program.cs`.
