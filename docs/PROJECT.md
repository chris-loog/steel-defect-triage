# Production Forecast Copilot – Project Documentation

> Living document. Updated at the end of each stage. Stage status lives in [`PROGRESS.md`](PROGRESS.md).

## 1. Purpose
A small portfolio MVP showing an end-to-end Data & AI workflow for **production planning** in a
manufacturing / ERP context. It forecasts how many units a production line will produce in each of the
next 24 hours, and an LLM explains that forecast in plain language for a production planner
(digital-twin style view of the line).

This is a production project, not an energy project: the signal is **units produced**, not kWh or load.

## 2. Domain & target
- **Signal:** hourly output of one production line (`units_produced`).
- **Forecast target:** the next 24 hourly `units_produced` values.
- **Planner questions it answers:** When is output highest/lowest tomorrow? Where are the dips
  (shift changes, planned maintenance)? How does tomorrow compare with today?

## 3. Data source – simulated production line
No public dataset with real hourly production output was found (companies rarely publish it; searched
Hugging Face, Oct 2026). The data is therefore generated by a small Python **production-line simulator**
("digital twin") and is always labelled as simulated.

Simulator: `forecasting/simulate.py` (run `python simulate.py` in `forecasting/`, seed 42 → reproducible).
- 2 years hourly (Oct 2024 – Sep 2026), one line, nominal 120 units/h.
- Shifts: early 06–14, late 14–22, night 22–06 Mon–Fri; Saturday early only; Sunday and holidays off.
  Efficiency early 100 %, late 97 %, night 90 %; first hour of each shift 85 % (handover).
- Planned maintenance: every 2nd Saturday early shift (0 output).
- Breakdowns: random, ~1.5/week, 1–4 h, 0 output (not forecastable).
- Changeovers: ~2/week, product A/B/C, 40 % output in that hour, extra scrap.
- Noise ±5 %, scrap 2–4 % → `good_units`.

Output: `data/production_hourly.csv` – columns `timestamp, shift, product, status, units_produced,
scrap_units, good_units`. Target = `units_produced`. `status` is for exploration and LLM context only
(not a model feature – unknown in the future).

Exploration: `forecasting/notebooks/01_explore.ipynb`. Baseline MAE on the last 8 weeks:
same hour yesterday **40.6**, same hour last week 16.3 units/hour.

## 4. Architecture
```
data/ (simulated CSV) → forecasting/ (Python: pandas, scikit-learn, FastAPI)
                      → backend/ForecastCopilot.Api (ASP.NET Core, typed HttpClient, Chart.js UI)
                      → LLM (local Ollama by default) writes a short summary for the planner
```
Docker Compose runs both services. Azure deployment is optional.

## 5. Forecasting approach
- Model: RandomForest / GradientBoosting (`forecasting/train.py`); the one with the lower test MAE is saved.
- Features (`forecasting/features.py`): hour of day, day of week, lag 24h, lag 168h. All are known 24 h
  ahead, so one model predicts each of the next 24 hours directly (no recursive forecasting).
- Split: time-based, last 8 weeks = test set (never shuffled).
- Baseline: "same hour yesterday". The model must beat it on MAE (mean absolute error).
- Results (test MAE, units/hour, simulated data):

  | Model | MAE |
  |---|---|
  | Baseline: same hour yesterday | 40.6 |
  | Baseline: same hour last week | 16.3 |
  | RandomForest (saved) | **10.3** |
  | GradientBoosting | 10.5 |

  Remaining error is mostly random breakdowns, which cannot be forecast.
- The LLM never produces numbers; it only describes the structured forecast JSON.

## 6. How to run
```bash
cd forecasting
python -m venv .venv && .venv/bin/pip install -q -r requirements.txt
.venv/bin/python simulate.py   # regenerate data/production_hourly.csv (seed 42)
.venv/bin/python train.py      # train → model/model.joblib (gitignored) + model/metrics.json
```
